# Project modes and transitions

Oasis Harness has two persistent project modes. 개척 모드 / Pioneer focuses on
the owner's requested development or investigation in one Pioneer chat.
오아시스 모드 / Oasis applies the existing Oasis, Cameleer, Camel and Calf roles
and rules. Neither mode imposes a universal product-completion threshold: the
owner's purpose and scope govern each task. The protected eight-core contract
and version remain unchanged; `oasis-pioneer` is a separate default skill beside
Harness Doctor. The distribution has ten default and fifteen optional skills.

## Selection and installation

`extensions.workflow.mode` in `.oasis/project.json` is `pioneer` or `oasis`.
Keep its schema version and exact top-level keys. The neutral donor template
does not bind a particular project mode. A fresh installation plan records the
target-specific selection and its classification evidence, while retaining the
original donor bytes as immutable bases.

| Actual target | Default |
|---|---|
| Fresh empty project, including only Git/license/guidance/environment preparation | Pioneer |
| Fresh existing program, application source, code-bearing scaffold or product data | Oasis |
| Existing valid installation with no stored mode | Oasis compatibility fallback |
| Partial `.oasis/` without valid installation ownership | Recovery/ownership decision before initialization |

An explicit initial selection overrides the fresh default. Inspect the actual
files instead of guessing from directory names. Setup configuration containing
inline application commands is program material; ambiguous/malformed package
configuration receives the conservative Oasis default with its path retained
for review. Plain preparation commands and dependency-only configuration may
still be setup-only. Existing installations preserve
their selection through reinstall, upgrade and Doctor; missing legacy mode does
not silently initialize chats. A mode option on an update is not a mode switch.

The owner's fresh installation request includes selected-role initialization:
one visible Pioneer, or fresh visible Oasis plus Cameleer. Use native project and
caller evidence, review existing linked roles and reconcile uncertain ownership
before creating anything. An install-only request initializes waiting roles. An
install request containing a concrete application task may deliver that same
task after initialization. The raw file installer performs no native chat action;
the agent completes these native steps within the installation request. Git,
hooks, backup, publication, optional skills and global settings keep their own
selection and authority boundaries. See [installation](installation.md).

Mode persists until the owner explicitly switches it. Recognize the desert names,
`Pioneer` / `Oasis` and purpose names `프로토타입 개발` / `운영` in an actual switch
instruction. Definitions, quotes and instructions to document names are not
invocations. There is no automatic size threshold or temporary task-only
prototype mode. A demonstrated coordination or repeated-delivery need may
justify one brief recommendation; preserve a declined selection and do not
repeat the same reason or start monitoring.

## Work and worker authority

Pioneer investigates, implements, checks and retains knowledge directly. Use the
applicable engineering knowledge from ProjectGuide, Calf principles and local
project guides without loading unrelated rules or adopting Calf's reporting
route. Existing skill responsibilities may be refined from evidence inside the
assigned work. New/deleted skills and structural/core/authority changes remain
owner decisions. Consulting optional resources does not activate a capability.

Pioneer is visible and solo by default. An explicit visible-worker request uses
ordinary Developer task chats, one if no count is supplied. Actual IDs, project,
caller and assignment bind them to Pioneer; a `Developer_...` title alone proves
nothing. Their authorized result route is to their assigning Pioneer. They are
not Calfs and do not change the protected Camel topology. Explicit subagent
requests use the declared count and scope. For `서브에이전트로만 작업해`, delegate
code edits, tests and integration edits; Pioneer coordinates, reads, reviews,
reports and carries out already authorized operations.

Oasis keeps the existing responsibilities: Oasis maintains the harness and
knowledge, Cameleer manages priorities, Camel owns a bundle and Calf investigates,
implements and verifies it. No Camel/Calf or descendant sends to Cameleer,
including through a relay. Mode context must not carry their questions/results
around that rule; the human still relays them. Project file facts, durable guides
and Pioneer's own context may be used without impersonating descendant messages.
See [identity](identity.md).

## Planning and fast work

`계획작업으로 진행해` in Pioneer asks this same Pioneer to give only the waiting
acknowledgement requesting actual Codex Plan mode and the owner's planning start,
then wait without tools or reads. It creates no Camel. In Oasis it uses the
existing Camel `plan-wait` assignment. A prompt label cannot toggle native Plan
mode; current session metadata and exposed creation/messaging tools have no Plan
setter. Once the owner starts planning in actual Plan mode, discuss the plan.
Implementation requires a separate instruction; a toggle or plan approval does
not grant it. The canonical detailed rule is ProjectGuide's "Planning work".

`빠른 작업` / `fast work` is task pacing, independent of persistent mode. An
explicit request applies immediately to the current authorized task with prompt
implementation, brief directly relevant checks and exact deferred verification
and resume steps. It does not weaken implementation or external-write authority,
manual relay or settings preservation. It ends with the task or a changed owner
instruction. Generic requests to act quickly retain their actual scope and do
not alone select a named full-suite waiver. Pioneer's normal short checks are a
separate default. Definitions and quoted examples do not invoke pacing.

## Transition sequence

An explicit owner switch authorizes the following whole lifecycle. Prepare and
inspect its concrete plan; ask only about unresolved material conflicts or
unknown ownership, rather than repeating a generic mode-confirmation question.

1. Verify the actual root, project, host, caller, selected source/lane and linked
   role identities. Checkpoint current writers at a safe saved intermediate
   point. Preserve dirty/index state, unfinished work and exact resume information;
   do not mark unfinished work complete or cancelled.
2. Capture the requested goal/scope, status, decisions, relevant commands,
   performed versus deferred checks and open work. Retain reusable knowledge in
   its closest existing guide. Keep transient handover state and actual chat IDs
   under private `.oasis/local/`; it is neither a permanent knowledge ledger nor
   proof of approval. Do not copy whole transcripts or forbidden descendant
   messages.
3. Prepare fresh target chats: Pioneer for Oasis-to-Pioneer, or Oasis plus
   Cameleer for Pioneer-to-Oasis. A genuine later cycle always gets fresh chats;
   do not unarchive old owners. A healthy request for the already initialized mode
   is a no-op. An incomplete operation resumes its original targets and IDs.
4. Preserve verified caller settings, including model/reasoning, permissions and
   approval behavior. Verify saved settings through cold resume. Deliver bounded
   role/context prompts in the owner's conversation language, inspect actual
   first user messages and completed role waiting acknowledgements, and confirm
   standby. Metadata creation or caller-supplied success flags are insufficient.
   An exact first acknowledgement verifies that waiting response; it does not
   prove future skill selection, engineering decisions or all role behavior.
5. Only after every new target is verified, archive the explicitly linked old
   scope. Pioneer-to-Oasis includes old Pioneer and its linked ordinary Developer
   workers. Oasis-to-Pioneer includes connected Oasis/Cameleer/Camel/Calf, with
   leaves before parents. Preserve unrelated chats. Inspect native descendants
   because parent archival may cascade; an unscoped descendant or ambiguous
   ownership blocks the affected archive instead of guessing from titles.
6. Verify archive outcomes and finalize the persistent mode/bindings. Navigate
   to Pioneer or Cameleer; for Oasis also give the owner its Oasis link. Switch-only
   requests leave the new roles waiting. If the same human request explicitly
   assigns follow-up work, deliver it after the transition to Pioneer or Cameleer
   under its normal role flow. Do not automatically restart unfinished work.

No mode change edits Git profiles, hooks, accounts, services, backup bindings,
global Codex settings or actual native Plan mode. Existing source/lane readiness
requirements apply; the transition never silently changes checkout.

Checkpoint fingerprints cover the source/index and a regular-file inventory,
including covered project files outside Git tracking. The inventory omits private
`.oasis/local/` and directory trees named `.git`, `node_modules`, `.venv`, `venv`,
`.tox`, `.mypy_cache`, `.pytest_cache`, `.ruff_cache` and `__pycache__`. These
dependency/cache contents remain outside the inventory's drift proof; the CLI
does not modify them. Git HEAD/index/diff evidence remains separate. Unreadable
covered inventory or a covered link/reparse path needs reconciliation before
native actions; omission is not a successful checkpoint check.

## Commands and native evidence

Installed adopters invoke `python -B -X utf8 tools/oasis.py`; source operators use
their source entry point. Inspect `workflow --help` and each subcommand's help
before constructing a command. These commands support agent-assisted operation;
they do not offer a CLI-only create/message/archive shortcut.

| Command | Purpose |
|---|---|
| `workflow status` | Distinguish selected mode, initialized role bindings and pending transition |
| `workflow plan` | Prepare exact old/new scope, context, settings/source prerequisites and archive targets |
| `workflow start` | Start a private journal and prepare target metadata within the reviewed operation |
| `workflow inspect` | Reconcile actual native state and identify the next authorized action |
| `workflow resume` | Continue that same operation from observed evidence; finalize only after required facts are verified |

`workflow plan --target <project> --mode pioneer|oasis` accepts the actual
`--source-thread-id` (normally `CODEX_THREAD_ID`), the selected managed
`--lane main|test`, `--language ko|en`, and optional `--context-file`,
`--bindings-file` and `--task-file`. `--output` saves a new UTF-8 plan only below
the target's private `.oasis/local/` and refuses an existing file. Inspect the
exact prompt/archive scope and then use
`workflow start <plan.json> --authority <owner-request-reference>`. An authority
reference records the real request; the string itself is not proof of consent.

For example, after reviewing the actual checkpoint and bindings, prepare a
Pioneer-to-Oasis switch with trusted installed commands:

```powershell
python -B -X utf8 tools/oasis.py workflow plan --target . --mode oasis --context-file .oasis/local/checkpoint.json --language ko --output .oasis/local/mode-plan.json
python -B -X utf8 tools/oasis.py workflow start .oasis/local/mode-plan.json --authority '<actual-owner-request-reference>'
```

Substitute the audited source/lane and actual private paths; a command example
does not authorize a switch. Keep the returned receipt path for later inspect
and resume. Do not use shell output encoding or edit the sealed plan to disguise
different prompt bytes.

Context JSON uses only `purpose`, `status`, `decisions`, `commands`, `checked`,
`unperformed`, `open_work` and `resume`. For a transition, include the saved
checkpoint status and unfinished/resume information. These fields carry project
facts and the allowed handover, not automatically forwarded role messages.
`--task-file` contains the exact UTF-8 work explicitly assigned in the same human
request; omit it for switch-only waiting. Keep task authorization separate from
merely mentioning unfinished work in context.

For role ownership not yet in workflow state, `--bindings-file` contains a JSON
array of reviewed bindings. Each uses an actual `role`, `thread_id`,
`parent_thread_id` (null for a primary) and `first_user_message_sha256`. Supported
roles are Pioneer, Oasis, Cameleer, Developer, Camel and Calf. A reviewed
`Unrelated` row with null parent explicitly preserves an ordinary chat, including
one whose title resembles a role, without assigning it that role. The hash
is SHA256 of the actual reviewed native initial user text encoded as UTF-8;
multiple native text parts are joined by a newline. Prompt, acknowledgement and
task text hashes use the same raw-byte rule; plan/state object seals use canonical
JSON. A Developer's parent
is its Pioneer, Camel's parent is Cameleer and Calf's parent is its Camel. Inspect
all retained assignments/session receipts and native history before preparing
the array; a supplied ID/hash/title is not sufficient without that evidence.
New scoped Developer/Camel/Calf session receipts carry an `assignment_marker`
which the agent puts at the start of their first authorized role prompt. Planning
intakes these retained receipts, verifies the actual native first message and
matching parent before including connected workers. An unassigned, mismatching
or uncertain linked worker blocks the affected switch. The explicit bindings
file supports reviewed legacy roles without these markers; it does not permit
guessing ownership from a title.

`next_actions` supplies exact target IDs, prompt bytes or archive scope. Immediately
before each eligible native mutation, run
`workflow resume <receipt> --authority <reference> --begin-action <action-id>`
once. Use the returned exact action once through the supported app tool, then
run `workflow inspect <receipt>` to reconcile its actual outcome. Use existing
created target IDs for prompt delivery; do not create another chat. `assign` or
`task` maps to authorized messaging, `archive` to the scoped archive operation,
and the completed result's `navigation` to the primary chat UI. Do not navigate
or send follow-up work early merely because metadata exists. If an attempt is
already started but unobserved, inspection remains pending and replay is refused.

Native creation and saved-setting checks reuse the metadata-only session adapter;
it never sends `turn/start`. Actual first prompts, follow-up work, navigation and
archives use supported Codex app tools in the user's authorized lifecycle. Bind
evidence to actual project/root/host/caller/role IDs and prompt bytes, not a title
or a local assertion of delivery. Do not forge settings, write private app data,
change permission profiles or auto-accept an approval request to bypass a missing
capability. See [sessions](sessions.md) and the
[official App Server contract](https://learn.chatgpt.com/docs/app-server).

## Interrupted operations

Retain the plan, journal, target chats, prompts, responses and unknown outcomes.
Keep the old primary active until targets are ready. A timeout or lost response
does not prove an action failed: inspect actual native identities/messages/turns
and archive state before resuming. Never recreate a target or resend a prompt
just because a receipt is incomplete. Preserve a pending operation when evidence
is unavailable or ambiguous, and report its exact next inspection/resume action.
Once archival has begun, verify each completed leaf and resume the remaining
scope; never restore guessed bindings or claim an atomic rollback occurred.

Static checks and disposable fixtures establish their exercised boundaries only.
Live first-turn behavior, role adoption, UI navigation, native archival cascades
and real project trials require separate evidence. Diagnostic projects/chats and
cleanup need concrete owner authorization after preparation; routine installation
or a real requested switch is not an invitation to create additional test chats.
See [verification boundaries](validation.md).
