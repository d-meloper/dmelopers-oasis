# Verification boundaries

No status in this file is a transferable approval. Local tests are repeatable;
external-service evidence belongs to each installing project and stays local.

| Surface | Local evidence | Separate real verification |
|---|---|---|
| Files/install/update | Empty and existing project fixtures; transaction, concurrency, recovery, merge conflicts | Review actual project conflicts and final manifest |
| Skills | 8 protected core + default Doctor/Pioneer + 15 optional metadata/resources, activation, negative routing cases | Native catalog paths, model selection, old-chat adoption |
| Project modes | Fresh/legacy selection, preserved specialization/bases, verified-role transition and pending/resume fixtures | Real initialization, first-turn waiting, UI navigation, archive cascade and adoption |
| Session metadata | Lost-response reconciliation, restricted-policy persistence fixtures, no implicit turns | Approved diagnostic chat, cold resume, actual first-turn behavior |
| Git | Disposable repositories, common-state engine, historical branches, refs/index preservation | Actual project ownership and selected profile |
| Backup | Disposable external relay and remote-only inactive restore | Approved private repository, exact commit sync and independent restore |
| Publication | Injected remote, drift, unexpected/partial assets and response loss | Approved isolated public fixture, PR attachment, immutable release and anonymous download |
| Knowledge | Duplicate/generalization/core-intrusion/privacy blockers | Independent semantic review of actual evidence and applicability |

Run all local tests from the package root:
`python -B -X utf8 -m unittest discover -s tests -t . -v`.
The suite creates only disposable local filesystem/Git fixtures. Actual GitHub
writes and chat creation are deliberately absent. Read-only native protocol
availability is useful evidence but is not end-to-end session verification.

When the owner says `빠른 작업으로 진행해`, immediately apply fast work to the
current authorized task without another confirmation. Prioritize implementation
and a reproducible verification entry point. Use a brief relevant check
instead of spending the task on broad review or the full suite. Record the exact
deferred checks and required inputs; if no brief check is practical, mark it not
run. Describe the outcome as limited verification or ready for verification.
The full-suite command above remains the normal-depth path, not a prerequisite
for completing implementation under this task pacing. Project mode, role,
existing authority, plan-wait and
required external-write identity/byte checks remain unchanged. The shared trigger
and scope rule lives in the project's ProjectGuide; source operators reach it
through README. Recognition examples are guidance, not performed model evaluations.

For coordinated Oasis work, `계획작업으로 진행해` reuses the existing Camel `plan-wait` contract.
Its handoff includes a tool-free acknowledgement requesting that the owner
enable actual Codex Plan mode and start the conversation in the Camel. In Pioneer
the same initial acknowledgement/waiting stays in the existing Pioneer chat;
no Camel is created. An owner-established independent Oasis chat uses the
same-chat exception in the single `LocalGitWorkflow.md#independent-specialist-sessions`
contract at the installed project root (`seed/LocalGitWorkflow.md` in source).
Static
guidance/resource checks do not verify native mode switching, trigger recognition
by a real model or first-turn waiting. The session adapter remains metadata-only;
the currently exposed creation/messaging tools have no Plan mode setter. A live
trial must distinguish waiting, actual mode selection, owner-started planning,
plan approval and separately authorized implementation. Historical role trials
below do not establish behavior for the new mode-dependent invocation wording.

Independent-session evaluation must distinguish a real owner assignment from a
title, an actual requested task from a standing role or unfinished-work note,
and acknowledged resource release from silence or delivery. Exercise the shared
writer boundary, prohibited relays, next-handoff versus live instruction changes,
same-chat planning wait and mode-switch preservation of independent requests.
Portable guide/link checks do not prove native adoption or authorize a live
chat, external resource or domain operation. No new specialist registry or
protected core role is implied.

For behavioral evaluation, present the scenarios in each skill's references to
an independent reviewer without the expected answer first. Record selected role,
invocation/non-invocation, tools attempted, approval boundary and evidence in
`.oasis/local/evaluations`. Compare afterwards. A scenario document or exact
string assertion is not evidence that a model followed the rule.

Doctor local fixtures compare complete staged donor bytes rather than version
labels, exercise selected-skill three-way refresh, preserve independent project
knowledge/settings, and block conflicts, missing/corrupt bases, incoming core
drift, private payloads and self-installation. The helper is local audit/planning;
it does not fetch, apply, prove semantic approval or establish live discovery.
The original trials below describe the original eight-core/15-optional package;
they do not establish live recognition, private upstream access or updating for
Doctor, Pioneer or mode transitions. Doctor obtains all material owner decisions before
application; ordinary installer upgrades retain their active-skill preservation.

Project mode fixtures exercise deterministic configuration and native-evidence
state handling with injected session metadata/history. A journal entry, claimed
delivery flag or quoted acknowledgement does not itself prove model behavior.
Even an observed exact first acknowledgement establishes only that tool-free
waiting response, not future skill use or complete role adoption.
Meaningful transition checks must preserve old active roles until target standby,
avoid duplicate creation/prompt replay after uncertainty, validate linked IDs,
block unscoped archive descendants and retain unfinished work. Fresh default
selection specializes the target without changing its original donor base;
updates preserve mode/optional selections and do not initialize chats. Real
Codex first-turn responses, native archive cascades and existing-chat adoption
remain separate checks. See [workflows](workflows.md).

Source development version-hook fixtures use real disposable Git commits,
including amend, failed commit/retry, explicit minor-base selection and partial
staging in the version file. They verify one patch per successful commit, no
duplicate pending increment on retry, unchanged core bytes and preservation of
unrelated unstaged edits. Partial-path/alternate-index commits refuse before
version writes; ordinary staged commits cover the supported workflow. This hook
is configured only for the owner's primary source repository, not adopter defaults.

For live validation, first prepare neutral fixture bytes, exact diagnostic
project/chat titles, intended permission inheritance, target repository/account
IDs, repository creation/protection changes, release tag/channel, candidate
hashes and cleanup expectations. Obtain the owner's concrete authorization only
after these are reviewable. Never reuse a project's production repository for
the preview trial. Retain failed, denied, partial and manual checks explicitly.

Historical baseline implementation verification includes these performed neutral trials:

- Two empty projects with different selected capabilities installed and upgraded
  without Git initialization. Native discovery found the expected 9 and 10 local
  skills respectively, with no catalog errors; all 23 skill definitions passed
  metadata validation. The source inventory maps all 26 skill families and 69
  resources. Ten independent request scenarios were reviewed without supplying
  the expected answers first; this is narrower evidence than exhaustive model
  evaluation of every capability.
- Four real role chats exercised actual project identity, inherited settings,
  cold-resume persistence, first-turn guidance, a tool-free plan-wait response,
  separate planning and implementation instructions, scoped file execution and
  one Calf-to-Camel result. Camel retained its result for manual owner relay.
  An existing Oasis chat explicitly reloaded updated instructions and manuals.
  Recorded turn settings establish configuration, not backend model attestation
  or automatic adoption by all existing chats.
- A private repository received the exact neutral commit through an external
  relay. Independent remote-only restore with unavailable original source and
  relay paths recovered exact tracked bytes and refs without active hooks,
  remotes or inherited backup binding. Automatic backup activation was outside
  that live fixture; its failure behavior is covered by local tests.
- Separate stable and preview repositories completed approved PR, squash,
  draft, upload and immutable publication. Stable exported selected source and
  an artifact; preview published only an artifact. Independent metadata and
  anonymous downloads matched the approved candidate bytes, and repository
  protections remained intact.

Local tests cover deterministic failure/recovery, concurrency, preserved state,
uncertain responses and negative authority/routing cases. The final execution
record, exact package digest, commands and outcomes stay with the implementing
project; this document conveys neither those private identifiers nor approval.
Run the suite against the actual installed version before relying on changes.

Public URL adoption adds exact-source review before executing donor code, safe
local initialization and native discovery without copying source authority.
Initial collision resolutions bind current hashes and reviewed merged bytes while
keeping immutable donor bases. Tests cover preserved existing ignore/guidance and
license files, plan drift and later three-way updates. Distribution intake and
transaction/recovery reject Git/Codex/private-evidence paths and linked roots.

Installed payload tests check the explicit adopter manual/runtime inventory,
absence of source-only account/repository/check names and tooling, unchanged core,
and retirement of old owned development files with local specializations retained.
Project publication remains opt-in and uses that project's explicit binding.
Source development verification policy belongs only to the source's development
guide and tools, which the installer excludes.

Observed live defects in saved-setting representations, redirected Unicode
reporting and installed manuals were corrected and rechecked. Overbroad initial
authority retrieval was retained as a procedural deviation and informed the
communication guidance; the later file success does not erase it. See lessons
K39-K42. No further live model rerun is claimed for the wording correction.

Limits remain explicit: unsupported richer permission-profile representations
stop before chat creation; check-run-only CI integrations need a verified
adapter; source-only publication has local rather than live trial evidence.
External provider changes and project-specific tools, builds, scanners, stores,
mail or runtime behavior require their own configuration and scoped validation.

Source-root Windows validation reproduced access-denied errors while replacing
publication state files in disposable local fixtures. The observed holder was
not identified; antivirus or another reader remains a hypothesis. Atomic writes
now retry only Windows replacement errors 5 and 32, using the same flushed
temporary bytes for at most six attempts and 0.62 seconds of scheduled delay.
Each attempt rechecks the destination for links/reparse points. No destination
is deleted, permission changed or external request replayed to obtain success.
Permanent denial and unrelated errors still propagate. A native Windows handle
fixture demonstrates recovery after a reader releases its replacement-blocking
handle; injected permanent-denial fixtures retain old bytes and bound retries.
See [Windows sharing semantics](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew).
This local mechanism does not identify the original holder or establish live
publication behavior; failed runs remain in the implementing root's local record.
