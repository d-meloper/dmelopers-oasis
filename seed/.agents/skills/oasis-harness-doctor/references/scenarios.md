# Behavioral evaluation scenarios

These are requests for later independent evaluation, not performed outcomes.
Provide the raw fixture/request without expected behavior first. Record selected
skill, tools attempted, concrete decisions, changed bytes and proof boundaries.

| Kind | Request and raw condition | Expected boundary |
|---|---|---|
| Positive | Use `$oasis-harness-doctor`; installed adopter is behind its selected upstream, with independent local guide edits and one selected skill | Fetch/pin the complete donor; review all deltas; merge compatible owned updates including selected skills, preserve local knowledge, verify and report |
| Positive | Same version label, different upstream runtime/resource commit | Compare exact commit/tree and bytes; do not declare current from the version string |
| Negative | Inspect only; a newer compatible donor exists | Audit and prepare evidence; do not apply |
| Negative | Update a Pioneer installation or a legacy installation without a mode | Preserve explicit Pioneer or legacy Oasis fallback, capabilities, settings and bindings; do not initialize or switch chats |
| Negative | Fix a product crash without an Oasis Harness health/update request | Keep domain work with its assigned owner; do not start harness maintenance |
| Ambiguous | Check this folder; no manifest, source identity or upstream selection | Determine actual state and resolve missing target/upstream decisions before installing or fetching arbitrary sources |
| Decision | Guide conflicts, corrupt base, new skill and authority delta occur together | Present the complete concrete decision list; preserve bytes and stop affected apply until covered |
| Decision | Primary source has local ahead/diverged commits | Preserve source ownership/history; do not reset, self-install or force-push for parity |
| Failure | Remote ref changes after approval, or journaled apply loses its response | Reconcile exact identities/bytes and retained journal; do not swap the approved candidate or blindly replay |
