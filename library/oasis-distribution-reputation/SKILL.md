# Distribution Reputation

## Prerequisites and scope

The exact reported download/site, published identity, warning evidence and a suitable vendor channel. Submitting a report needs explicit authority.

Read the selected project contract and actual tool capabilities. Installation or discovery grants no external authority. Existing human authorization applies only to its exact scope; obtain missing concrete authority before the effect. Preserve core roles and manual owner relay.

## Workflow and recovery

Separate reputation, actual malware detection, signature failure and byte mismatch. Resolve the exact source URL, redirect behavior, released artifact hash and applicable signature. A signed or scanned file is not guaranteed safe; a warning is not by itself proof of maliciousness.

Reproduce only within requested execution scope and preserve the warning's exact context without collecting unnecessary personal data. Prepare a concrete concise report containing the affected identity, relevant evidence and requested correction. Use an available provider workflow; missing account/capability is a prerequisite, not a reason to invent a submission endpoint.

Submit only to the exact authorized target and retain its real acknowledgement. Do not disable protection, add broad exceptions, weaken update trust or submit unrelated binaries. Reconcile uncertain submission by its case identity before repeating. Report vendor receipt separately from accepted correction or changed distribution behavior.

Use [acceptance scenarios](references/acceptance.md) for changed decision boundaries. Source/fixture checks, installed behavior and live reflection are distinct. Retain failed, unknown and not-run outcomes. Improve existing project-local guidance from evidence; structural/core changes need approval. No automatic upstream propagation or monitoring.
